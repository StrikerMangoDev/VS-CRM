# VS CRM on a 2 GB Google Cloud VM

This deployment runs the existing app and PostgreSQL on one Debian 12 `e2-small` VM. Build the Linux image on the development computer, then transfer the tested image; do not build on the 2 GB production VM. There is no load balancer, Cloud SQL instance, NAT gateway or autoscaling group in this design.

The primary hostname is `vscrm.orgogo.com`. The original `vscrm-136-83-129-156.sslip.io` hostname remains an HTTPS alias during DNS cache propagation. The separate `crm.orgogo.com` application and its DNS record are untouched.

## Before provisioning

Select the exact project/account, billing account, region/zone, HTTPS hostname and administrator email. Do not reuse another application's resources or local demo database. Confirm the project billing link and estimated regional VM/disk/IP charges. Use on-demand Linux, a 30 GB balanced persistent disk and one public IP. A billing alert is a notification, not a hard cap on Compute Engine charges.

Use a dedicated VPC/subnet and VM service account with the cloud-platform OAuth scope. Allow public TCP 80/443 only to the CRM VM; permit SSH only through IAP's documented source range. Do not expose PostgreSQL or the Next.js port. Enable Shielded VM protections. Grant the VM service account object-creator access only to the private backup bucket and Secret Manager accessor only on `vscrm-runtime`. Do not grant it access to `vscrm-administrator`. The private bucket uses public access prevention, uniform bucket access and a 14-day lifecycle.

## Install

1. Build `docker build -t vscrm:<release> .` locally and save the image. Record its image ID and the transfer archive's SHA-256.
2. On the new VM, run `install-host.sh` as root. Transfer/load the checked image, and place compose.yaml (named compose.yaml), Caddyfile and backup.sh under `/opt/vscrm`.
3. Store runtime JSON in Secret Manager (`POSTGRES_PASSWORD`: 64 hexadecimal characters; optional `SMTP_PASSWORD`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`, `SMARTFLO_API_TOKEN`). For an existing database preserve its password when migrating storage. Create root-owned mode-0600 `/opt/vscrm/.env` with only `APP_IMAGE`, `CRM_HOSTNAME` and nonsensitive integration configuration. Create `backup.env` with `BACKUP_BUCKET`. Never put secret values in these files. Install `fetch-secrets.py`, `public-env.py`, `runtime-entrypoint.cjs`, `rotate-admin.cjs` under `/opt/vscrm`. Put the pinned numeric resource `projects/722607882915/secrets/vscrm-runtime/versions/1` in root-owned mode-0600 `secret-resource`. Install `vscrm-secrets.service` and `docker-secrets.conf` as `/etc/systemd/system/docker.service.d/vscrm-secrets.conf`; reload systemd and start the secret service before Docker. It fetches through VM identity into `/run/vscrm` (root-only directory, UID 1000 read-only files), and Docker requires it at boot. Failed retrieval prevents Docker startup. Secrets remain accessible to privileged host administrators and running processes; `/run` and process memory may use the encrypted VM disk's swap.
4. In `/opt/vscrm`, run `docker compose up -d db`, then `docker compose run --rm app node node_modules/prisma/build/index.js migrate deploy`. These migrations are for a new empty database. Existing databases require a schema comparison and backup first.
5. Pipe a private JSON document containing `email` and a random password of at least 20 characters into `docker compose run --rm -T app node deploy/bootstrap-admin.cjs`. The bootstrap refuses to overwrite existing users. Keep credentials out of shell arguments, logs and the image. No demo accounts are provisioned.
6. Run `docker compose up -d`. Point the approved hostname to the VM and let Caddy obtain its HTTPS certificate. Verify the certificate, HTTP-to-HTTPS redirect, secure login cookie, authenticated screens and database-backed writes. Verify public access to ports 3000/5432 is blocked.
7. Run the first backup manually. Restore the dump into a separate temporary test database and compare key record counts before removing that test database. Install the backup service/timer in `/etc/systemd/system`, run `systemctl daemon-reload`, and enable the timer only after the manual backup succeeds. Check its next run and service status.

## Operations and rollback

Use `docker compose ps`, `docker stats --no-stream`, `systemctl status vscrm-backup.service` and `systemctl list-timers vscrm-backup.timer` to inspect runtime and backup health. Check VM memory, swap and disk usage after initial real use and before large imports. The app has an 896 MB container limit, PostgreSQL 512 MB and Caddy 128 MB; 2 GB is a starting configuration, not a throughput guarantee.

Before an update, take a fresh verified backup and record the running image ID. Keep the previous release image and nonsensitive configuration. Change only APP_IMAGE, run compatible additive migrations, and recreate the app service. All Compose `run app ...` commands use the secret-loading entrypoint, including migrations and bootstrap. Do not bypass that entrypoint with `exec` for database maintenance. Roll back the image only when schema compatible, retaining the secret-managed configuration. Never restore the old plaintext `.env`, or run `docker compose down -v` on production.

To refresh a runtime secret, pin its new numeric version in `secret-resource`, stop the containers, restart `vscrm-secrets.service`, start `docker.service`, and recreate containers so bind mounts use the new files. A database password change additionally requires coordinating `ALTER ROLE`; changing the secret alone cannot rotate an existing PostgreSQL user. Back up first. To rotate the administrator, pipe private JSON containing `email` and a random password (24–72 bytes) into `docker compose run --rm -T app node deploy/rotate-admin.cjs`. This hashes the password, clears reset credentials and revokes that administrator's sessions transactionally. Store the login in the separate human-access-only administrator secret and a user-only local file; never print it or pass it in command arguments. After restoring an older backup, rotate the administrator again and revoke restored sessions. Application-managed Drive OAuth tokens, if configured later, are separate database records and need their own storage migration.

To upgrade, take a backup, stop the VM, change its machine type to e2-medium, start it and review the container memory limits. This causes downtime. The single VM design has no failover; independent backups reduce data-loss risk but do not prevent outages. SMTP, Drive and carrier acceptance remain separate until configured and tested.
